Keeping an IDE away from your keys

Notes on sandboxing JetBrains and VS Code on a Linux laptop, so that a hostile repository or a misled AI agent cannot reach SSH keys, GitHub tokens and other secrets.

Short version

  • Opening a project already runs its code. The sandbox has to contain the IDE's own indexing and build machinery and its AI agent, not only the terminal.
  • Neither JetBrains nor Microsoft documents a supported way to run the whole IDE inside a sandbox. Their dev container and remote modes are built for convenience, and both vendors treat the link between the two halves as trusted.
  • On Linux, a sandboxed IDE can still be an ordinary desktop window: bind the Wayland socket into the sandbox and nothing else. The recipes for this are community posts, not vendor documentation.
  • Three tools came up for doing it. Bubblewrap is a mature building block, ai-jail is popular but seven months old, and jailbee is new and has one author. None is a finished answer for a graphical IDE.
  • For code from a stranger, such as a recruiter's take-home test, the tools' own documentation says to use a disposable virtual machine.

Researched on 7 October 2026 from public sources, which are linked throughout and listed at the end. Nothing on this page was tested hands-on. A claim marked untested comes from general knowledge, not from a source that was checked.

Why opening a project is enough

The fake-recruiter campaign known as Contagious Interview asks a developer to open a repository for a code review or a coding test. The repository carries a .vscode/tasks.json file with a task set to run when the folder opens, and that task downloads the malware. GitLab's write-up notes that forks of VS Code are affected in the same way.

VS Code asks whether you trust a workspace before running tasks, but it asks once. After that, a later pull can add a malicious task with no new prompt, as this summary of Abstract Security's analysis describes. OpenSourceMalware lists what the payload goes looking for, which includes wallet and key files in the home directory.

JetBrains IDEs have their own versions of this: Gradle or Maven sync runs build scripts, and package install hooks, test runners and language servers all execute project code untested. An AI agent adds a second route, because instructions planted in a README or a code comment can steer it.

How strong each boundary is

BoundaryStrengthNotes
Toolbx or DistroboxNoneThe container gets your home directory, external storage and devices. Fedora's documentation says not to treat Toolbx as a sandbox, and Distrobox's author has declined to add a sandboxed mode.
Namespace sandbox or container with only the project mountedGoodBubblewrap, rootless Podman, Incus containers. Shares the host kernel, so a kernel bug is a way out. Never mount the Docker socket into it.
Virtual machine per projectStrongSeparate kernel. Use no shared folders, and snapshot or delete when done. Costs memory, and graphics and clipboard are bridged.
Separate machine or cloud VMStrongestThe right place for anything from a stranger.

An immutable host such as Fedora Silverblue protects the operating system. The keys, tokens and browser sessions an attacker wants are in the home directory, which is as writable there as anywhere else.

Two ways to run the IDE

What the vendors say about the split model

  • VS Code forwards credentials by default. The Dev Containers extension shares local Git credentials and automatically forwards a running SSH agent. Settings exist to reduce this, but one user reported SSH to GitHub still working from the container after turning them off, and a request for a single switch to disable all sharing is open.
  • VS Code's remote link runs both ways. Microsoft's Remote-SSH page warns that a compromised remote could use the connection to execute code on your local machine. Calif demonstrated it: an extension on the remote side opens a terminal on the local machine.
  • JetBrains is similar in principle. Its remote development security model says information on either side may be forwarded to the other without user interaction, and names GitHub authorization as a case where that happens in the background. SSH agent forwarding is a checkbox under Tools, SSH Forwarding; the default was not confirmed.
  • Hardening is possible but fiddly. Community guides for locking down a VS Code dev container blank out the forwarding variables and delete sockets that VS Code injects, and note that VS Code puts some of them back. Another states plainly that VS Code dev containers are not a security boundary.

A sandboxed IDE as a native window

A virtual machine has its own display, so graphics and the clipboard are bridged by guest agents, which is where the rough edges come from. A container or namespace sandbox is ordinary host processes with a restricted view. If you bind the compositor's Wayland socket into it, the IDE talks to the real compositor, and you get a normal window with native scaling, copy and paste, and drag and drop.

JetBrains IDEs run natively on Wayland by default from 2026.1, so the socket is all the display access they need. JetBrains' Remote Development client does not yet enable Wayland automatically.

Shared into the sandboxWhat you getRisk
Wayland socketNative windows, clipboard, inputModest. Apps cannot read each other's windows or keystrokes, but the IDE can read and replace the clipboard while it has focus.
X11 socketOlder applicationsHigh. Any X client can log keys and capture other X windows. Do not share it.
GPU device (/dev/dri)Hardware accelerationExposes the host kernel's GPU driver, a large interface. Optional: start without it.
D-Bus session bus, rest of the runtime directoryNotifications, keyring, opening linksHigh. These reach the keyring and other desktop services. Leave them out.
  • This is Linux only. On macOS, Linux containers run inside a virtual machine, so there is no native-window path.
  • Compositors differ. Some offer extra protocols for screen capture or clipboard monitoring to any client. The security-context protocol lets a sandbox mark its connection so the compositor can restrict those. Flatpak uses it; a hand-written sandbox does not get it automatically.
  • A VM with a real GPU share may be coming. Intel's Linux driver officially supports GPU virtualization on Panther Lake, though Intel had not said which products get it.
  • Per-window forwarding from a VM. Tools such as waypipe can show a VM's application windows on the host desktop, keeping the separate kernel at the cost of some latency untested.

What vendors and distributions say

No official guidance was found from JetBrains, Microsoft, Canonical or Fedora for running a full IDE in a container with a Wayland socket.

Packaged builds do not help

  • The IntelliJ IDEA Community Flatpak requests the whole host filesystem, all devices and the SSH agent socket.
  • The VS Code Flatpak is an unofficial build and holds a permission that lets it run commands on the host.
  • The Snap builds of both IDEs use classic confinement, which is no sandbox untested.

Community recipes worth reading

  • Podman with a Wayland socket. Fedora forum threads on running a graphical app isolated from the filesystem and on getting Wayland apps to start.
  • Incus. A maintained profile for graphical apps in Incus containers, tested with Ubuntu 24.04 as host. It shares Wayland, X and audio, so trim it to Wayland.
  • Bubblewrap. Ivan Molodetskikh's script creates a fresh home and binds only the Wayland socket into a new runtime directory. Joachim Breitner's setup runs VS Code and its extensions inside the sandbox with a separate development home.

Bubblewrap, ai-jail and jailbee

None of the three uses Podman or Docker as the sandbox. Bubblewrap and ai-jail are not containers in the image sense: they run the host's own programs inside restricted namespaces. jailbee uses Incus system containers, each with its own operating system image.

Bubblewrap is mature and ships in every major distribution. ai-jail is popular, changes almost daily and is mostly one author. jailbee is in effect a one-person project with almost no outside users yet.

Guides for a specific IDE, and for recruiter scams

  • JetBrains. Only jailbee has first-class support: jailbee ide launches the IDE from the container, using a JetBrains Toolbox install on the host. No guide was found for a JetBrains IDE under Bubblewrap or ai-jail. The nearest, opencode-bubblewrap, sandboxes an agent that a JetBrains IDE talks to, not the IDE.
  • VS Code. Joachim Breitner's post runs VS Code inside Bubblewrap, over X11. Nothing specific was found for ai-jail or jailbee. One ai-jail walkthrough exists for a terminal agent under WSL.
  • Recruiter scams. None of the three mentions them. Atlassian's write-up recommends a dedicated, isolated environment for take-home tests and setting VS Code's task.allowAutomaticTasks to off, without naming a tool.

  • Trial host. An Ubuntu 26.04 VM covers all three. jailbee's installation guide recommends it and does not mention Fedora. Bubblewrap and ai-jail should also work on Silverblue untested.
  • VS Code inside another sandbox. VS Code is built on Chromium, which brings its own sandbox, and that can misbehave when nested. JetBrains IDEs mostly avoid the problem untested.

Whichever sandbox you pick

Secrets per project

  • Main SSH key. Keep it out of every sandbox and do not forward the agent. A hardware-backed key that needs a touch cannot be copied even if the host is compromised.
  • Git access. Generate a key inside the sandbox and register it as a deploy key for that one repository, or use a fine-grained GitHub token limited to that repository with a short expiry.
  • Other secrets. Inject only what the project needs, and prefer short-lived cloud credentials.
  • The limit of isolation. Anything you put inside can still be sent out by code running there, including the IDE's own AI sign-in. Outbound network rules are the only control for that.
  • Git on the host. Do not run Git on the host against a working tree the sandbox can write to. Hooks and repository configuration can execute commands. Run Git inside.

Building and testing

  • The toolchain lives inside the sandbox, and builds, tests and debugging run there as they would locally.
  • For Python, install uv inside and let it manage interpreter versions. Keep .venv inside the sandbox and put the uv cache on a persistent volume so rebuilds stay fast.
  • Tests that need Docker should use Podman or Docker running inside the sandbox, never the host's socket.
  • Reach a web app under development through a forwarded port.

Take-home tests from recruiters

Never open one on a machine or profile that holds anything you care about. Use a throwaway VM with no shared folders, or a cloud environment in the browser, and delete it afterwards. Pressure to run the code quickly, or before a call, is the usual tell. If you think a machine was compromised, Atlassian's advice is to reimage it; deleting the repository is not enough.

Open questions

This looked like something that would be a solved, common setup by now, and it does not seem to be. Answers from anyone who has done this would help.

  • Does anyone run a full JetBrains IDE or VS Code inside Bubblewrap, Podman or Incus day to day? What broke, and what did you have to let through?
  • Has anyone checked what still reaches a dev container after credential forwarding is turned off, in either IDE?
  • On Fedora, what is the smallest SELinux change that lets a rootless container use the Wayland socket?
  • Is software rendering acceptable for a JetBrains IDE on a high-resolution panel, or is the GPU device needed in practice?
  • How do you issue per-project credentials (deploy keys, fine-grained tokens) without it turning into a chore?
  • Is there a tool or write-up this page missed?

Other projects seen

These turned up during the search and were not evaluated.

  • code-on-incus: Incus containers for AI coding tools, with a written security model that covers Git hooks and editor configuration.
  • devc: reads a devcontainer.json, starts it with Podman or Docker and exposes it as an SSH host for an editor. Agent forwarding is opt-in.
  • Bento: deny-by-default sandbox for scripts and agent actions, built on Bubblewrap, seccomp and Landlock.
  • Qubes OS: an operating system built around one virtual machine per activity, for anyone who wants this model throughout.
